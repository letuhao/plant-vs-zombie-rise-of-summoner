# Party dungeon — design review 2026-09-05

**Record of the six-lens structured review of [party-dungeon-ideal.md](../party-dungeon-ideal.md), synthesised the same day. Companion to the ideal; the ideal's ✅ boxes remain binding, and §5 below lists the forks put back to the owner.**

**Reviewed:** `docs/architecture/party-dungeon-ideal.md` (1,711 lines, Parts I and II, the sixteen ✅ owner
decisions under §8 and §11.9 taken as binding). Six independent passes: **design red-team** (D1–D18),
**architecture and code verification** (A1–A10 plus a 44-citation spot-check), **numerics, power ladder
and economy** (N1–N15), **seedsmith and generation contract** (G1–G20), **player surface, standalone-first,
process and ownership** (P1–P21), **prior art** (R1–R14 plus a fifteen-number verification table). This
synthesis read all six, then opened every file cited in a disagreement — code beats docs beats comments.

**Counts.** 98 findings (18 · 10 · 15 · 20 · 21 · 14). After dedup: **9 S1 clusters**, **17 S2 clusters**,
14 S3/S4 rows, **11 owner forks**, 22 exact edits to the ideal, 9 stale-doc propagations owed elsewhere.
Four findings downgraded and four code citations corrected (§9).

**Verdict.** The mechanics are ready for `/spec`: one ladder holds under arithmetic (every magnitude reaches
`P(Θ)` through `Wm·DangerBand` and `contentScale`, the contest table is exact to three decimals, no anchor
field is a number), the layer rule holds (zero injector hits), and the sixteen decisions are all
implementable. **The capability map cannot be drawn yet**, for three reasons that are not mechanics: (1) four
`decisions.md` rows or retractions are owed before modules may be named — the sixth stage and its new id, the
store-side shape of decision 5, the two ADRs decision 4 needs, and the five-slot lock decision 16 changes;
(2) decision 11's second half claims a module two other programs already own, and only the owner can retract
it; (3) the ideal carries six premises the spec would inherit as wrong facts — autopilot "free", drop count
"rises with depth", "fifth stage", the DD2 provisioning claim, "WReact 0", and the "hand-authored floor"
that decision 6 retired — each is a one-sentence edit (§6). One mechanics defect is S1 on its own: per-room
`MatchEndEarn` makes two row-1 fights the best soul faucet in the game; the fix is one sentence.

## 1. Verdicts on the disagreements (a)–(i)

**(a) Decision 5 blast radius — architecture (A1) is right; surface (P12) misread the remedy list as code.**
`TurnEngine.Step` is reached only from `RpgStore.WorldTurns.cs:510` and `:607`, both inside a commit for one
`world_id`; a delve stored as its own `rpg_worlds` row is never iterated by the map world's turn, so "a mode
filter in every world query" is work that does not exist. The real breakage is exactly A1's list, verified:
`WorldValidation.Validate` (`WorldValidation.cs:26-41`, called at `RpgStore.World.cs:188`) throws on rule 1
(`:71-111`, every room kind must be a `SectorTypeCatalog` row — which `/api/world/catalog`,
`WorldEndpoints.cs:259`, would then serve to the frozen map FE), rule 4 (`:165-181`, exactly one Home owned
by a player faction holding a Seat), rule 5 (`:184-194`; `boss-lair` has `CanHostSeat = true` at
`SectorTypeCatalog.cs:98`, so a boss room on that type needs exactly one Seat), rule 6 (`:198-220`), rule 11
(`:328-332`, `Sectors.Single(Home)`), rule 13 (`:349-354`, `WorldTemplateCatalog.SizeIdOf` throws for any
id but two, `WorldTemplateCatalog.cs:25-30`; `template_id` is `NOT NULL`, `RpgStore.World.cs:23`).
`GetActiveWorld` is `WHERE player_id=$p AND state='active' ORDER BY world_id LIMIT 1`
(`RpgStore.World.cs:384-388`) and the FE bootstrap is `GET /api/world/{playerId}` (`WorldEndpoints.cs:28-32`) —

`ProfileForExpedition`, and never through `WebMatchService.ProfileForWave`, which returns `null` →
`classic-round` for any id not in `WaveCatalog` (`WebMatchService.cs:53-56`; A5) — with a one-clause

**(c) The once-entry +7 — survives, with the D2 conditions, and one honest correction to the doc's reachability
argument.** Arithmetic (numerics table, recomputed from `BattleModels.cs:190-193`): +7 bands = +35 Θ; at
parity with the surrounding content our hit is σ(−6.9) ≈ 0.001, theirs ≈ 1.000, their crit ≈ 0.73. The
doc's own §11.2 calls +20 "impossible"; this is 15 past it. Decision 7's rung 10 (+3) and the tail stack on
top unless the spec says otherwise — nothing in the box says otherwise — giving +50 Θ at "once impossible".
It is legal: a band delta feeding row 23, one ladder, no multiplier, and it is a tunable. **N1 is the
correction:** the doc says Dave level and runs close the gap; today the squad-side contest reads the
*specimen level* — `BattleStatComposer.cs:105-108` sets `theta = setup.Index` ("no real power-index
composition is wired through BattleActorSetup yet") and `WebMatchService.cs:396-403` fills `Level` from
`s.Actor.Level`. So the actor-side `Θ_actor` composition is a **wiring gap** the ideal's §2.3 must list, and
until it lands a +35 gap costs 35 specimen levels per demon, not 35 Dave levels. **Ruling:** the owner's +7
stands as written. The spec adds: the picker shows the *effective* band name, never the delta; sealing is on
extraction or boss kill, and a wipe leaves the domain open (the box says "archived at extraction, sealed
afterwards" — a wipe is not an extraction); the stack rule is written (recommend: stacks, no cap on the rung
picker, effective band shown). "Very strong items" is honestly delivered by `bossRarityFloor` (breadth and
ceiling), because item level reads `Θ_room` (`LootPipeline.cs:170-175`) and a `many` domain seven bands
deeper drops the same item level. D2's alternative (fold +7 into the authored `dangerBand`, delete the knob)
contradicts an owner tunable → owner decision (§5 #2), not a fix.

**(d) Boss shield pool — compliant, and it needs a target statement and a registered read.** `ShieldGate.
AbsorbFinalized` (`ShieldGate.cs:51-63`) drains shields before the sink — a flat pre-HP pool, so D10 is right
that `share‰ × P(Θ_room) × (parties−1)` is functionally the per-party EHP multiplier §8 Q3 refused. Numerics is
also right: it is a magnitude reading `P(Θ)` once with the count on encounter design — row-21-shaped, not a new
§10 row. Prior art is right that the calibration exists in the repo: Risk of Rain 2's `playerFactor =
1 + 0.3·(playerCount − 1)` (`08-endless-scaling-meta-progression.md:66`) is the exact shape. **Target
statement for the spec:** *"The boss fight at N parties lasts within a tunable band of the solo fight's
length. `raid.modes.*.bossShieldPerPartyMilli` is a share of `P(Θ_room)` per extra party, derived from the
`bossW` ratio and the retinue count, never flat; starting shape 300‰ (RoR2's 0.3), with D10's 170‰ (flat
length under `W` doubling) as the lower reference. The read is registered in the §10 mirror with a PS-2
'read once' note so the next sweep does not find a private scale."* Monster Hunter's 100/163/200/234% is
Wilds only (R5) — label it.

**(e) Recruit and altar under decision 12 — minimal rules that keep teleport-home and remove dominance.**
Verified: a demon is a mint the Sanctum sells for `costPerPull: 100` (`summoning.v1.json:10`); a `pack`
fight pays 4–7 × `killDelta 1` × cs (`souls.v1.json:10`, `SoulEarnPolicy.cs:74-75`); base join 250‰
(`expeditions.v1.json:19`). At those numbers talk's EV is ≈5× fight's before the offer is priced, and the
doc prices the offer as a fraction of *room yield* — cents. Decision 12 is binding (home at once, bound if
a slot is free, never at risk). The minimal set: **(1)** the souls offer's floor is the altar pull price at
the room's Θ through `SoulSinkPolicy`, paid from *unbanked* souls — the offer *is* the bind price, the bind
stays free, decision 12 is untouched; the spirit, supply and released-demon offers are priced as equivalents.
With the offer ≈ the demon's mint value, `takes and leaves` is a real loss and always-talk stops dominating by
construction. **(2)** Altar pulls are not covered by decision 12 (it names recruits and captures); rule them
**at-risk haul on the delve ledger, delivered at extraction** (no pack cell, per the same "never usable in
it" reasoning) — or the altar spends banked treasury only. The first keeps P6's two horizons. **(3)** Capture
pays no `KillEarn` (as written) and spends a seal priced at the pull price; with S1-1 (victory souls once
at extraction) the "capture the last enemy = Victory" path stops paying twice. **(4)** §11.6's fourth offer
type ("an unbound demon from the pack") has no source under decision 12 — draw from the home roster via a
released contract or drop the row. D4's alternative (bind priced from unbanked souls, else arrives unbound)
adds a condition to "bound if a slot is free" → owner decision (§5 #3), recommended second.

**(f) Permadeath, revive, wipe — the timing is decided; the meaning of "downed" is not, and the wipe needs a
sentence.** The decision 1 box says *"Retired at extraction"*; §4.6 says *"every demon downed at any point"*.
The box wins: one assessment point, extraction — SPEC FIX plus an IDEAL EDIT to §4.6. `Retired` today is
written only by the release path (`RpgStore.UniqueActors.cs:205-216`; the ideal's own §2.2 at `:148` says
"tombstone set by release"), so extraction becomes a second producer — an FSM semantics change the spec
states and `unique-actor-runtime.md` records (P18), not a wiring gap. **Revive:** with `revive` supplies
and a guaranteed rest row, "standing at extraction" makes permadeath a consumable check. Recommend
`downedOnce`: on a permadeath rung a demon downed at any point is Retired at extraction even if revived — the
revive lets it finish the run, not escape the rule. This is the natural reading of "permanent death" and does
not contradict the box's timing, but it is arguable, so it is an owner confirmation (§5 #4). **Wipe:** on a
permadeath rung a wipe Retires every demon and drops the haul — the no-refund + unreloadable pairing §4.6
refused, chosen knowingly by decision 1. The spec states it and names the mitigation DD1 actually ships
(R2): cheap replacement — the pull price at the pin stays available, and the recovery ritual is priced at the
delve's Θ. Owner confirmation on the wipe rule, same item.

**(g) Difficulty table under decision 7 — the deltas stay; the columns beside them change.** Decision 7's
deltas (−2, −1, −1, 0, 0, +1, +1, +2, +2, +3) leave five twins, and rewards read `contentScale(Θ)` only:
`easy` (−1, hunger ×0.75, join +50‰) strictly dominates `medium` (−1, identity); `very-hard` is where
permadeath starts at exactly `hard`'s payout. On a band-1 domain very-easy/easy/medium all clamp to band 0
through `PowerIndexComposer.ClampNonNegative` (`:77-78`, whose comment justifies clamping as "absence, not
corruption" — a −2 delta is neither). `depth.bossBand: 6` is absolute while rows climb `entrance + row/2`,
so a rich entrance (3) over 11 rows puts the last corridor at band 8 and the boss at 6. **Corrected shape,
respecting "medium one below entrance" and "hard is the identity row":** (1) keep the owner's delta column
verbatim; (2) every rule rung carries a *reward-bearing* column its owner already holds — encounter design's
`enemyCountDelta` (souls through `KillEarn`) or loot's `loot.rooms.boss.rarityFloor`/`rarityShiftBand`
stepping one band per rung — and the validator reads *"neighbouring rungs differ in `bandDelta` or in a
reward-bearing column, never only in a penalty column"*; (3) the StS-A1 elite bump and every modifier the old
table hung on `hard` move one rung up, because `hard` is now the identity row — the golden narrative becomes
"a **hard** delve's golden moves only when the entrance band moves"; (4) a rung whose effective band would
clamp on this domain is **not offered** (a rule, not a clamp), and the planner assigns `many` domains a
`dangerBand` ≥ 2 so the first shipped domains show the whole ladder; (5) `depth.bossBand` becomes
`depth.bossBandDelta` on the last corridor row's band (starting +1), with rung and once deltas applied to the
boss uniformly, and the `boss-lair` copy goes (N13). If the owner would rather every rung move the band
(D3's alternative), that rewrites decision 7 → §5 #8.

**(h) Seedsmith order — a clarification of decision 13, not a contradiction.** The owner's words: sub-pipelines
run *"because a unique binds event / dungeon pattern / boss drop and needs its dependency seeds resolved
first"* — the principle is **dependencies first**. The listed sequence (domains → rooms → encounters → events →
loot tables → uniques) violates it in detail: the doc's own domain anchor references `roomPalette`,
`lootBinding`, `questPool`, `layoutTemplateId`; rooms reference `encounterRef`/`eventPool`; tables reference
uniques by id. `seed-contract.md:191-192` forbids forward and cyclic references, and `adapters/base.py:31-36`
derives ordering from `reference_fields` *"rather than from a hand-written stage label … precisely the
274-error incident."* So the tool already computes the order the owner asked for, and it is G10's DAG:
registries and species (with `threatBand`) → layouts, supplies → events, encounters → uniques → loot tables →
rooms → domains, with the **planner's domain plan** (cells, model-free) existing first — which is what
"domains first" correctly names. **Ruling:** no owner decision; a `dungeon` adapter with honest
`reference_fields` produces the order; the box gets a footnote (IDEAL EDIT) so nobody builds the literal
list.

# Architecture decisions

Locked for v1. Change here before changing code.

| World turn phase order | **Locked**: `Reveal → Movement → Sieges → Production → Growth → Pressure → Events → Snapshot → Intel`. Changing this list is changing the ruleset — it is spelled out in `TurnEngineTests` rather than derived, so it cannot drift quietly. **`Intel` moved from second-last to last on 2026-08-22 (`RulesetVersion` 2 → 3)**: claims settle in `Snapshot`, so recording belief before it left a faction unable to see that its *own* claim had succeeded — it re-filed the order and the engine dropped it as `claim.already-yours`, costing a turn every time. Belief is what you know at the end of the turn, and the end of the turn is after the turn has finished happening. Found by playing twenty turns, not by any test; the final acceptance golden did not move because belief converges within a turn, so only intermediate hashes changed. See [world/spec-turn-engine.md](world/spec-turn-engine.md) |

| Battle time model | **Battles run on virtual time — a discrete-event kernel, never wall-clock.** `1 tick = 1 ms` (integer `long`); a Future Event List ordered `(dueTick, seq)`; turn-based and real-time are the **same** kernel differing only in time-advance mechanism (next-event jump vs fixed-increment step). **A mode is data, not a code path** — enforced by an architecture test that fails if any kernel type references a profile id or switches on a profile enum. Profile is **resolved from an existing content id** (`WaveCatalog.Get(waveId).Profile ?? classic-round`) and **never serialized onto `BattleSetup`** (a field there moves all four expedition hashes). Per-actor FSM `Charging → Ready → Committed → Resolving → Recovering` plus `Downed` (HP ≤ 0 is veto-capable, never a terminal edge); `Incapacitated` is a **derived read** from StatusRuntime, never a cached remainder. Readiness accrues **work**, not a precomputed deadline, so mid-flight haste takes effect on the current turn. In scope by owner decision: reaction lane, side-scheduled press-turn, multi-actor rendezvous, and live interactive sessions — for which determinism becomes **`(setup, seed, decision-trace)`** and the boot sweep must **refuse** an incomplete trace rather than re-resolve it. Ideal: [battle-turn-ideal.md](battle-turn-ideal.md), map: [battle-timeline-map.md](battle-timeline-map.md), audit: [battle/audit-2026-08-21.md](battle/audit-2026-08-21.md). **Approved 2026-08-21, not yet built.** |

## Why REST and SignalR together

REST survives page refresh and is easy to inspect (`GET /api/stats`). SignalR pushes spawn/die/metrics and `reload-stats` without polling. Raw WebSocket would need reconnect and rooms built by hand.

## Why HTTP fallback on the injector

`Microsoft.AspNetCore.SignalR.Client` may fail to load inside this BepInEx IL2CPP host. The game must still apply last-known stats and ship events over HTTP.

## Why no SQLite in the injector

The plugin must stay a thin hook. Persistence belongs to the server so the web UI works with the game closed.

## Why in-process queues, not Memcached

Localhost, one game, one server. Extra processes add failure modes. Injector `ConcurrentQueue` + server `Channel` + one SQLite writer is the cache.

## Why batch SignalR `Events`, not per-event `Event`

At 120fps a fight is thousands of events/s. One `InvokeAsync("Event")` per row waits on the previous persist. HTTP already posts `{ events: [] }`. The hub must match.

## Why the server stamps `player_id`

The game does not know saves. Later RPG is per-save, not per-PC. Current player lives in SQLite; child rows copy `player_id` from the run opened at `board.start`.

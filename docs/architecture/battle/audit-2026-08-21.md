# Structured review — battle-timeline specs (2026-08-21)

Four independent passes ran against T1–T5 before any planning: a **design red-team** (attack the "one scheduler, three knobs" thesis), a **code-integration verifier** (every claim checked against the real engine with file:line evidence), a **forward-fit** pass (does the seam actually carry the next program — skills, attack, defence, movement?), and an **owner-side pass** on process and build order. This file records the debates, how each was adjudicated, and what changed. The spec amendments are applied; this file is the why.

## Verdict

**The clock and queue are sound. The action model on top of them was underbuilt, and the build order validated it in the wrong order.**

What survived unbroken: next-event vs fixed-increment advance over one `(dueTick, seq)` queue is correct discrete-event simulation, and `classic-round` genuinely is `hybrid-atb` with the knobs pinned. The containment story holds.

What did not: three named mechanics need kernel features rather than profile rows, and — the finding that reframed the program — **`ActionEnvelope` would have shipped at the T5 gate with zero consumers.** `classic-round` sets every envelope field to zero, so the central abstraction would have been locked without a single real mechanic passing through it. Of the 14 traits in `TraitBattleCatalog`, **none are actions on a timeline** and exactly one (`swift`) touches readiness.

Revised headline claim, replacing the ideal's:

> One virtual-time scheduler serves every mode where we own the clock. A mode is data **as long as the scheduling unit is one actor taking one action**. Economies that schedule a *side*, and actions that resolve *inside* another action's resolution, are kernel features that must be designed in — not profiled in.

## Debates and adjudications

### D1 — Dilation: keep it in the clock, or delete it? (red-team vs the ideal's own §4)

The red-team argued dilation is borrowed complexity: rational `(num,den)` arithmetic plus fractional carry, specced in T1 and tested in T4, serving only `hybrid-atb` — which has no content, no consumer, and no product commitment. Worse, it contradicts the ideal's own §4, which states that whether a battle unfolds over 40 seconds or resolves instantly is *"a playback decision, not a simulation one"* — and then puts dilation inside the simulation clock.

Nothing defended it. Server resolution is instantaneous; the server never needs dilation.

**Adjudicated: deleted from the kernel.** Dilation moves to the playback layer. This removes the rational arithmetic, the carry mechanism, and a chunk of T4's test matrix at zero product cost — and it removes a compounding factor from D5 (a client that owns dilation owns the clock, which would have put the dilation schedule into the determinism trace).

### D2 — Who owns CC duration: the FSM or StatusRuntime? (verifier vs the T2 spec)

T2 said a suspended actor's pending timer is cancelled and its **remaining ticks stored**. Both the verifier and the forward-fit pass rejected this, from different directions.

The verifier's case is decisive: CC lifetime is mutated through five paths the FSM cannot see — `UpsertInstance` Refresh/Replace stacking, `ApplyFamilyMutex` displacement, `ClearGrant`, `WithdrawEntity` (called on both retreat and death), and the expiry prune. A cached remainder goes stale on every one. And the boundary pairing is load-bearing: `StatusRuntime` prunes on `ExpiresAt < now` (strict) while `IsCcLocked` tests `ExpiresAt >= now` (inclusive), so an instance expiring exactly at `now` survives and still locks — a 1000 ms CC locks exactly one round. An FSM remainder counting to zero resumes one round early. Byte-identity break.

The forward-fit pass added the corollary: since byte-identity forces `classic-round` to keep querying `StatusRuntime`, a stored remainder would be **dead code in the only profile that ships**.

**Adjudicated: `StatusRuntime` owns CC.** `Incapacitated` becomes a *derived read* at the seat-check point, never stored state. T2 amended.

### D3 — SMT press-turn: build side-scheduling, or cut the reference? (red-team vs the owner's named references)

The red-team showed `ITurnEconomy` as shaped cannot express Press Turn: the budget is **per side**, it is mutated by **resolution outcome** (weakness refunds, miss costs double), and most fatally the **scheduled entity is the side**, which then picks an actor. The kernel schedules per-actor readiness and holds per-actor slots; there is no side object anywhere in T1–T4. Modelling it per-actor requires readiness to read a shared side budget mutated mid-turn, which makes readiness impure and reintroduces exactly the branch T4's architecture test forbids.

The forward-fit pass reached the same wall from slot acquisition: two of three planned economies need a scope the single global `W` cannot express.

Against cutting: the owner named Shin Megami Tensei explicitly, and press-turn is what gives SMT its identity.

**Adjudicated: split the difference, and stop overclaiming.** Slot acquisition routes through the economy (`economy.TryAcquire`) rather than `ActionSlots` deciding alone — cheap now, and it makes side-scoped economies *possible*. Full side-scheduling (`ISchedulable` = actor | side, plus an `OnActionResolved` outcome hook) is **deferred to T6 with the economy decision**, and the specs stop claiming press-turn is a plug-in today. **This is an owner decision, surfaced below.**

### D4 — Is the seam validated at the gate? (forward-fit + red-team + owner pass, three-way convergence)

Three independent passes hit the same wall. Forward-fit: the envelope has no consumer at T5. Red-team: T4's serialization test is **vacuous** — with `ActionEnvelope.NoOp` (all zeros), "exactly one actor is ever in Committed/Resolving" passes for *any* value of `W`, so the test proving the program's headline knob would be green and meaningless. Owner pass: a coverage matrix showing `classic-round` exercises the FSM path and next-event advance in its most degenerate form, and **nothing else** — with zero wind-up, `Commitment` is unobservable; with `W=N` and simultaneous readiness, slot contention is unobservable; with constant readiness, the readiness function is unobservable.

**Adjudicated: the build order was wrong.** A validation profile with a **real action and non-zero wind-up** lands *before* T5. `W` is proven by contrast (assert serialization at `W=1` and overlap at `W=2` in the same file), not by an assertion that passes vacuously. And Checkpoint B splits into **B1 safety** (byte-identity) and **B2 capability** (a demanding profile runs a real battle) — because T5 passing proves nothing regressed, not that the design works.

### D5 — The four-clock problem, and when the subsystems move (forward-fit vs verifier)

The forward-fit pass found the program's justification unfulfilled: the ideal and map both say the kernel exists because "a DoT that pulses every 1000 ms is a scheduled event" and that rebasing fixes the sub-round under-delivery — but **no module in T1–T8 migrates `StatusRuntime` onto the queue.** After T5 there would be four clocks: the tick clock, `host.Clock.UtcNow` (`DateTimeOffset`, drives statuses), shield round-ticks, and the round quantum.

The verifier then proved the harder half: byte-identity **requires deliberately preserving the bug**. Verified end to end — `TickBudget` defaults to 1, `Tick` fires at most one pulse per call, and the clock jumps a full round; a `PeriodMs=250, DurationMs=4000` status delivers **4 pulses where the true schedule has 16**. A competent kernel that schedules pulses at their true times delivers 16, which is correct *and fails the gate*. Shields are worse: `BattleEngine.cs:182-183` ceilings shield `DurationMs` into **rounds**, `shields.Tick` takes a round index, and the regen carry (`ratePm * deltaMs / 1000`) truncates to **zero for any rate below 1000‰** if driven at 1 ms granularity — shield regen would silently vanish.

**Adjudicated: two explicit phases, and the program's payoff is honestly re-labelled.**
- **T5 preserves today's behavior**, including the under-delivery, and states so as a named hazard.
- **New module T9 `subsystems-on-timeline`** moves status pulses and shield upkeep onto kernel ticks, **after** the gate and **before** E1 — as a *deliberate behavior change* with a `RulesetVersion` bump, a golden re-bless, and a win-rate sweep. It cannot ride under byte-identity, and pretending otherwise would have produced a mystery gate failure.
- Mitigating discovery (owner pass): T9 may be much cheaper than feared. `StatusRuntime.Tick` already contains a bounded catch-up loop, so the kernel can drive it *at true pulse times* with an exact ms→`DateTimeOffset` conversion — no rewrite of `StatusRuntime` required. Shields need real work; statuses may not.

### D6 — Where does the profile id live? (verifier vs the owner pass)

The verifier found an unflagged gate-killer: `ExpeditionBattlePlan` embeds the full `BattleSetup`, and the expedition goldens hash the serialized resolution with default options (`DefaultIgnoreCondition = Never`), so **any** new property on `BattleSetup`/`BattleActorSetup` serializes on every actor in every plan and moves all four hashes — even at its default value. The precedent is recorded in the test file itself: adding `InnateShield` did exactly this. The two golden families have **opposite** sensitivities: setup fields move expedition hashes, report fields move battle hashes.

So the profile must be a `Resolve` parameter, not a field. But the owner pass found the countervailing constraint: **53 call sites** of `BattleEngine.Resolve(setup, seed)` across 11 files (including a sixth test project, `FusionRpg.E2E.Tests`, with 131 tests). A signature change silently violates T5's "the existing test suite passes unedited" acceptance criterion.

**Adjudicated: both constraints hold simultaneously.** `Resolve(setup, seed)` survives verbatim as an overload defaulting to `classic-round`; `Resolve(setup, seed, profile)` is a new overload. A profile id on the serialized records becomes a named **Never** in T5.

### D7 — Reactions and defence: stance, or true interrupt? (forward-fit vs red-team)

Both found the same hole — `Committed → Resolving` is observable only by the acting actor, so a defender has no event to react to — but proposed different shapes. Forward-fit offered a cheap out: **declared stance** (block is a normal action beforehand whose effect is `ApplyStatus("guarding")`, read by the resolver), which fits the current kernel with *zero* change and is exactly how `guardian`/`loyal` already work. The red-team wanted a **reaction lane**: a second slot pool `WReact` (default 0) plus a bounded nested-resolution stack, with the precedent that this codebase already runs `ProcDepthLimit` and an event-pipeline generation cap for the same shape.

**Adjudicated: buy the option, don't pay for the feature.** The pending resolve is **published as a cancellable handle** at commit time rather than living as an implicit timer — an addition to T2's contract, not a sixth state. `WReact` defaults to 0, so reactions cost nothing until used. This is sequenced **before T5** because it changes *when* the resolve is scheduled, and retrofitting it after the gate would move goldens. Stance-based defence remains available and needs nothing.

## Findings adopted into specs (condensed)

**T1 `virtual-time-core`**
1. `Advance` becomes `TryAdvance → Advanced | Blocked(reason)`. A jumping clock has no wall-time to dwell in, so an interactive `galaxy-sync` battle would jump straight past its input window. Signature change — must land now.
2. Dilation deleted (D1).
3. `Reschedule` **preserves `Seq`**. T1 already forbade cancel from renumbering; reschedule was silent, and a delay effect implemented as cancel+insert would silently reorder unrelated actors and make every golden history-dependent.
4. Frame→tick conversion is carry-corrected **inside** the clock, and the signature takes `long frames`, never a float-derived millisecond count: at 60 fps, Δ=16 loses 0.667 ms/frame — **2.4 seconds of drift per minute**. The purity guard extends to callers, since a float entering at the call site left the guard green.
5. Corrected claim: "1 tick = 1 ms means no unit translation" is **false** for two subsystems — shields run on round-ticks, `StatusRuntime` on `DateTimeOffset`. Both need adapter translation.
6. `Schedule` must not allocate per event (T1 covered the drain path, not the insert path).
7. Boundary: simultaneous resolution is explicitly out of scope — the kernel is strictly sequential, so no profile can produce "both die." Recorded so nobody infers otherwise from `W=N`.

**T2 `turn-fsm`**
1. New state **`Downed`** — hp ≤ 0, present, targetable, revivable. Without it, an immortal actor transitions `Resolving → Dead` (terminal) and the revive attempts `Dead → Charging`, which is not in the table, which **throws** — a crash at the most expensive checkpoint in the program. `Downed → Dead` on the scheduled sweep; `Downed → Charging` on revive. On-kill and on-death triggers hang here.
2. Missing transitions added: `Ready/Committed/Recovering/Incapacitated → Withdrawn` (retreat is checked after *every* dispatch, mid-round, so a `Ready` actor can retreat today) and `Resolving/Incapacitated → Dead`. Plus a **meta-test asserting the transition table against the documented diagram**, so a drawing omission can never again become a runtime throw.
3. `Incapacitated` is a **derived read**, not a stored remainder (D2).
4. `IIntentSource` seam: `TryDeclare(actor) → Intent?`. The kernel gated `Ready → Committed` on "an intent exists" while targeting was out of scope — a predicate it could not evaluate, with no defined false case. **No legal intent ⇒ the actor takes no slot, emits `action.passed`, reschedules at `now + PassQuantum`.** Without this, `galaxy-sync` at `W=1` deadlocks: the queue drains, the clock stops.
5. Pending resolve published as a cancellable handle (D7); `WReact` defaults to 0.
6. Post-apply trigger phase — a slot-free, FSM-neutral point after every HP delta where veto / on-kill / threshold listeners run in deterministic order. `immortal`, `soul-eater`, and `coward` are all this shape and none fit "an actor decides to act."
7. Envelope amendments: `Cost` → **`TimeCostTicks`** (three different costs shared one name; a content author reads `Cost = 30` as mana); `Rank` **relocated to the actor/readiness call** (on the envelope it multiplied into the same product as `Cost`, making them algebraically one number and losing the FFX actor-scoped/action-scoped distinction it was borrowed from); added `ActionId` (the envelope had no identity, so `skill.used` could not name what fired), `CooldownKey` (a `Category` class with no discriminator), `SlotConsuming` (movement and periodic pulses must not consume the `W` slot — at `W=1` only one actor could ever move), speed-channel selector (readiness hardcoded `turn.speed`, making "moves fast, attacks slowly" inexpressible despite the reserved `moveSpeed` vocabulary), `PriorityBand` (always-first effects are a scheduling override, not a cost multiplier — and impossible to retrofit, since it changes the sort key), `Interruptible` + refund, and `ResolveOffsets[]` for multi-hit. `CooldownClass.Global` dropped — no mechanic in this game needs a GCD.
8. Cooldown state has an owner and a start point (commit / resolve / end-of-recovery), and its interaction with suspension is stated.
9. `Commitment` clarified: it snapshots the **whole request**, not just the target — `berserker` reads the attacker's own HP and `bloodthirsty` picks lowest-HP, both of which need a defined read point once wind-up is non-zero.
10. EarlyBound + death rule written down: resolves against a **commit-time snapshot**; if the target is not active at resolve the action **fizzles** — consumes economy and full recovery, refunds no readiness. Keeps slot accounting identical on both paths so `W=1` cannot deadlock on the fizzle branch.

**T3 `readiness-model`**
1. **Readiness stores work, not a deadline.** The formula was evaluated once at schedule time, so mid-flight haste did nothing — "I hasted my mage and nothing happened this turn," in the mode whose identity is speed-driven turn order. FFX CTB decrements every tick and ATB fills continuously; a precomputed deadline is equivalent **only while speed and haste are constant**. The ideal's claim that "FFX CTB is literally this" was wrong in the case that matters. Store `(accruedWork, rate)`; rebase via `Reschedule` when `turn.speed`/`turn.haste` mutate. Same fix for suspension: store work, not time.
2. `DerivedStatRegistry.RegisterDefaults` added to the structure list with **non-zero defaults** — the registry validates by name with prefix fallbacks only for `status.*`, so `turn.*` modifiers would throw `UnknownDerivedChannelException` through the compose path. Haste defaulting to 0 would mean instant actions; speed 0 hits the divide-by-zero clamp on every actor.
3. Slot acquisition routes through `ITurnEconomy` (D3).
4. Verified and kept: flat non-elemental channels stay out of the generated roster and leave `AllCombatChannelIds` at 84.

**T4 `mode-profiles`**
1. The `pvz-realtime` row is **deleted**. Three of five knobs were inapplicable, T4 ships three profiles and never mentions it, the dependency graph draws T7 with a dotted *vocabulary-only* edge from T2 rather than from T4, and §6 says in prose that PvZ is observed. The table stated the acceptance rule "adding a mode is a row, not a branch" immediately below a row that was not a row. The scheduler serves **three** modes; the state *vocabulary* serves four.
2. `WScope : Global | PerSide` — a single global integer cannot express "one actor per side, alternating."
3. The serialization test is rewritten to use non-zero `WindupTicks` and to prove `W` **by contrast** (D4).
4. Stated coupling: `W` only binds when wind-up is non-zero, because atomic `Resolving` under a total order already serializes. And `W` is a knob, not *the* knob — what actually separates `classic-round` from `hybrid-atb` is the advance policy and the readiness function.

**T5 `kernel-adoption`**
1. New **Never**: no field may be added to `BattleSetup`/`BattleActorSetup` (moves expedition hashes) or `BattleReport`/`BattleActorResult` (moves battle hashes). Profile selection is a `Resolve` overload (D6).
2. Four hazards added to the existing three:
   - **CC-locked actors still draw initiative.** The filter is `Active` (alive and not retreated); CC is applied *after* seating. An FSM that suspends before seating removes one draw and desyncs every subsequent round from a single stun.
   - **Status pulse under-delivery must be preserved** (D5) — and **no test covers it today**, because every existing caller uses `PeriodMs: 1000` where one-pulse-per-round is accidentally correct. A sub-round fixture lands *before* adoption.
   - **Funnel window count is semantic.** The HP clamp is per-FA10, not per-delta; a merged window nets regen against DoT *before* clamping, a net-zero merged window emits **no FA10 at all**, and `EffectId` attribution belongs to whichever call enqueued first. An actor at 1 HP with −5 DoT and +10 regen survives at 6 in one window and **dies** in two. The specs already said "one funnel window" — what was missing was *why*, so this becomes an explicit Never.
   - **The early exit cancels shield upkeep.** When a battle ends on status damage, that round's upkeep and drain never run. Scheduled upkeep events will fire unless the exit explicitly cancels them.
3. Parity ladder corrections: record draw **values, not counts** — `SeededRng.NextUInt` uses rejection sampling, so one logical draw consumes a variable number of generator steps and a count assertion is meaningless. The `crit` stream is data-dependent twice over (gated on hit, and short-circuited when `pHit` is 0 or 1), so a trace assuming two draws per attack produces false failures. Full draw-site census recorded in the spec.
4. The parity ladder needs a **seam to observe draws**: `SeededRng` is `sealed`, has no counter and no interface, and the engine constructs its streams internally. Fix: an `internal` draw log — pure observation, no algorithm change, so `RngAlgoVersion` stays 1.
5. The gate covers **six** test projects — Core, Data, Guard, CheatCore, Launcher, **and E2E** (131 tests, calls the engine twice, previously omitted from verification sweeps).
6. Implicit control flow transcribed as declared facts: the `break` on a null target aborts the whole dispatch phase rather than one turn; `ReviveImmortals` sits between two flushes and gates on a `HashSet`; `DamageDealt` tallies pre-absorb and pre-guardian-split; kill attribution iterates `{target, guardian}` in fixed order; `rounds` serves four roles at once; the trailing drain stamps mid-round events with the last round number.

**Program-level**
1. New module **T9 `subsystems-on-timeline`** (D5), sequenced after T5 and before E1, with its own `RulesetVersion` bump and sweep.
2. A **`decisions.md` row is required before build** — AGENTS.md makes architecture changes that lock behavior a hard boundary, and no battle-time-model row exists. This program locks: the virtual-time DES kernel, tick = 1 ms, and the mode-as-data rule.
3. Latent, filed not fixed: `EffectFunnel.DrainOnce` still iterates raw dictionary order — currently unobservable because each slot mutates an independent actor and battle uses a no-op fx sink, but that safety rests on exactly the property a scheduler refactor could break. (Separately, `decisions.md`'s "Combat resolution SSOT" row is stale — it still says battle adoption is gated on the battle stream.)

## Owner decisions surfaced

1. **SMT press-turn** (D3) — build side-scheduling into the kernel (`ISchedulable` = actor | side, outcome-fed economy), or ship an actor-scheduled kernel and drop press-turn from the SMT reference? Turn-based SMT-*style* combat works without it; press-turn specifically does not.
2. **Defence shape** (D7) — is declared stance sufficient, or is true react-to-this-swing interruption required? Stance costs nothing; interruption is bought now and unaffordable later.
3. **FF15 link-strikes** — multi-actor coordinated actions have no rendezvous primitive and `W=1` makes them structurally impossible. FF15 is largely *built* on them. If that feel is the real target this is Critical; if not, the reference should be cut.
4. **T9's re-bless** (D5) — fixing sub-round pulse timing is a deliberate behavior change requiring a golden re-bless and a win-rate sweep. Confirm before T9 is planned.

## What survived the attack

- **The advance-policy unification.** No mechanic in the three scheduled modes needs a third time-advance mechanism.
- **`classic-round` as a degenerate parameter set** — constant readiness + 1000-tick quantum + `W=N` really does reproduce round-robin.
- **T4's no-branch architecture test** — scanning the kernel for profile-id references is the right way to make the thesis falsifiable in CI rather than in prose. Kept, and still written before the profiles.
- **T5's parity ladder** — stream → phase → per-round state → event sequence → hash, with fixtures captured before any engine change, was called the best-engineered part of the corpus. Kept and corrected (values not counts).
- **Two invariants that came from actually reading the prior art:** `max(1, …)` on readiness (a zero-tick result under next-event advance is an infinite loop that never advances the clock) and `RoundDiv` round-half-up (FFX floors here and ships turn-order inconsistencies as a result).
- **T1's queue shape** — `(dueTick, seq)`, tombstone cancellation that does not renumber, caller-owned drain buffers — with the caveat that tombstones are the wrong shape for an observed mode (T7 is stateless projection: no queue, no scheduling, no per-actor machine).

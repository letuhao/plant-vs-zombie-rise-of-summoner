# Audit — action program spec set, 2026-08-22

A review pass over the ten module specs before planning. Findings are graded **Critical** (would ship a defect), **Important** (would be discovered painfully during build), **Minor** (worth stating).

Three Criticals were found by reading shipped code rather than the specs. Fixes are applied to the specs named; this document is the record of why.

---

## Critical

### C1 — `Core/Actions/` has no determinism guard at all

`A1` §9 sites the action runtime **outside** `Core/Battle/Timeline/`, and that reasoning is correct: `TargetResolver` uses LINQ, which the tick-path rules ban.

But the guard carries **two** rule sets, and moving out of the folder drops both:

| Rule set | Protects | Applies to `Core/Actions/` today |
|---|---|---|
| `BannedOnTickPath` — LINQ, scene scans, stat resolves | Frame cost | Correctly not wanted |
| `BannedEverywhere` — wall clock, `Random`, `Guid.NewGuid`, `.GetHashCode(`, floating point, dictionary enumeration | **Byte-identical replay** | **Nothing enforces it** |

Verified: `KernelPurityScan.Scan` is invoked on exactly one directory — `src/FusionRpg.Core/Battle/Timeline`. So a `DateTime.UtcNow`, an ambient `Random`, or a `double` in the action path compiles, passes CI, and silently breaks every replay and every golden that touches it.

This is the exact failure mode the purity rules exist for, and the action path is *more* exposed than the kernel because it makes decisions rather than just scheduling them.

> **Fix: scan `Core/Actions/` with purity rules only, tick-path exempt.** The mechanism already exists — `DiagnosticsExemptFromTickPath` does precisely this for `BattleTrace.cs`. It is a directory and an exemption entry, not new machinery.

Applied to: **A1** (boundaries + structure), **A2** (boundaries).

### C2 — `Random` targeting has no RNG stream

`TargetResolver.PickRandom` takes an injected `ICombatRng`, which is why the resolver is replay-safe. **No spec says which stream an action passes it.**

The battle's named streams are `initiative`, `crit`, `essence`, and `status`. There is no `target`. So an action using `Mode = Random` either draws from an unnamed source — nondeterministic — or borrows an existing stream and **desyncs every draw after it**. The second is worse, because it produces a plausible battle that does not replay.

> **Fix: name a `target` stream, derived like the others.** And state the consequence: a new stream is inert until first drawn from, so adding it is free — but the **first action that uses `Random` is golden-affecting**, and belongs in the movers bucket.

Applied to: **A2** (design + testing).

### C3 — A2's "no per-call dictionary" claim is false

`A2` says precompiling `TargetSpec[2]` avoids a per-call dictionary. It does not. Inside the shipped resolver:

```csharp
var map = JsonOverlay.FromObject(filters);   // FilterPool, every Resolve call
```

The filter dictionary is **re-parsed on every resolve**, and precompiling the outer `TargetSpec` does not reach inside `FilterPool`. `A7` evaluates usability across actions × targets every turn, so this is a parse per candidate, not per action.

> **Fix: state it honestly and bound it.** Either the action path calls a pre-filtered pool (filters applied once at compile into a predicate over `BoardEntitySnap`), or the cost is accepted and measured. The spec must not claim a property the shipped code does not have — that is how a perf assumption becomes a perf surprise.

Applied to: **A2** (design + testing).

## Important

### I1 — `A1` §4 is structural, not just an ordering question

`A1` §4 asks whether an action applies its own atoms or they flow through the actor's priority-sorted effect list, and treats it as an ordering detail. It is not.

**If atoms flow through the effect list, `rpg_action_effect_scope` cannot be implemented.** The effect list has no notion of the action's resolved targets, so `eachTarget` and `primaryTarget` have nothing to resolve against. The answer decides whether one of `A1`'s three tables exists.

Applied to: **A1** — §4 now states the table dependency.

### I2 — `priority_band` is being used for two different things

On the envelope it is a **scheduling** override, part of the event queue's sort key — documented as impossible to retrofit for exactly that reason. `A7` uses it as **AI preference order**.

One column, two meanings, and they will disagree the first time an always-first effect is not the AI's first choice.

> **Fix: `A7` sorts on its own key** — action tag preference, then `action_id` ordinal. `priority_band` stays a scheduling concept.

Applied to: **A7**.

### I3 — Action binding has no table

`A1` says intrinsic actions come from the species row and granted ones reuse `effect_binding`'s owner vocabulary. It never says **how an action is bound** — `effect_binding` points at an `instance_id`, not an `action_id`.

`A4`'s gate 1 and `A7`'s per-actor hoist both depend on answering "which actions does this actor hold", and neither can be built without it.

Applied to: **A1** — an explicit binding shape.

### I4 — "Run" has no identity

`A3` stores pool state on "a per-member row on the run". Expeditions have `rpg_expeditions`; the world map has entities and turns; a one-off skirmish has **no run row at all**.

Three different structures and one missing one. `A3` needs a run identity that either exists or is created — otherwise "persist across a run" cannot be implemented for the case that is easiest to test.

Applied to: **A3**.

### I5 — There are three cross-program asks, not two

The map lists two. `A6` adds a third: **action rows joining the content hash** is a change to `E8`, which is the atom program's module.

Applied to: **map §10.7**.

### I6 — Range is evaluated in two places

`A4` gate 4 asks *"is any target in range"*; `A2`'s gate asks *"which targets qualify"*. Both are real questions, and both need the same Chebyshev function against the same board.

Not a contradiction, but two implementations of one rule is how they drift. One function, two callers, stated.

Applied to: **A2** and **A4**.

## Minor

### M1 — Nothing emits to `BattleTrace`

The timeline program makes determinism `(setup, seed, decision-trace)` for interactive modes, and the boot sweep must **refuse** an incomplete trace. Actions are the decisions being traced, and no spec says what an action emits.

Not blocking wave 1 — auto-resolved battles need no trace — but `A7` is where the decision happens, so it is the natural owner, and retrofitting a trace after selection ships means re-deriving what was chosen.

Applied to: **A7** — a note, not a requirement.

## Round 2 — cross-spec pass

The first round reviewed each spec against the code. This round reviews them **against each other and against the build order**, which is where the remaining defects were.

### R2-1 (Important) — `A4`'s affordability gate is built before the cost system exists

Build order is `A1 → A2 → A4 → A5 → A3 → …`. `A4` gate 3 reads the cost table. **`A3` owns the cost table and lands two modules later.**

So `A4` ships with a gate that has nothing to query. Options, and the first is right:

> **Gate 3 is a seam from day one and a no-op until `A3`.** `IAffordabilityCheck` returns "affordable" while no cost system exists, and `A3` supplies the real implementation.

The alternative — reordering `A3` before `A5` — is worse: it puts the cost system inside the byte-identity gate for an action that has no costs, which is exactly the coupling the current order avoids.

Applied to: **A4**.

### R2-2 (Important) — no wave-1 action consumes a slot, and no module proves the integration

`A5`'s basic attack is `slot_consuming = false` (the round loop has no `W` contention). `A9`'s movement is `slot_consuming = false` deliberately. **Nothing in this program's ten modules exercises a slot-consuming action.**

The kernel's own slot tests are thorough (`W` proven by contrast, all five exit paths releasing), but they drive `ActionSlots` directly. The **action → slot** path — commit acquires, resolve releases, fizzle releases, interrupt releases — is unproven by any module here.

The timeline program's `B12` is where a real action runs under a real profile, and it is the natural owner. **Stated as a dependency rather than left as a hole**: this program does not prove `W`, and it must not be assumed to.

Applied to: **map §10.7**, as an explicit coverage boundary.

### R2-3 (Minor) — `A6`'s compile stage went stale when C3 was fixed

`A6` §2 describes compiling `ActionTargetSpec → TargetSpec[2]`. After C3, filters also compile into a predicate over `BoardEntitySnap` rather than travelling as a dictionary. The compile stage table no longer lists everything it compiles.

Applied to: **A6**.

### R2-4 (Important) — the action layer's cost ceiling is the sweep, and no spec names it

Every spec here is careful about allocation, and none states a **budget**. The kernel has one (0.15 ms/frame) because it runs inside a Unity frame. Actions run server-side, so there is no frame — which makes it easy to conclude there is no ceiling.

There is one, and it is the **win-rate sweep**: thousands of battles resolved back to back with no player, where `A7` evaluates actions × targets every turn of every battle. A sweep that takes minutes is a tool; one that takes hours is abandoned, and the balance discipline it supports goes with it.

> **The action layer's perf contract is "the sweep stays a tool you actually run"**, measured in battles per second rather than milliseconds per frame. `A7`'s gate hoisting (`A4` §1) is the main lever, and its `FactReader.Reads` test is the right instrument — it just needs a stated target.

Applied to: **A7**.

## What the audit did not find

Worth recording, so a later pass does not re-check them:

- **No contradiction between specs** on the sealed decisions — resources, grid, golden ordering, and the membership rule are used consistently across all ten.
- **No second system** was introduced: one targeting stack, one condition language, one scaling mechanism, one binding vocabulary, one applier.
- **The byte-identity story holds.** `A5`'s freeze depends on three things — no-board range passes, `SourceOrder` targeting, and the zero envelope — and each is asserted in the spec that owns it plus again in `A5`.

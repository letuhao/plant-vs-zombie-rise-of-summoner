Why one affix cannot print a percentage. For the four SigmoidPoints channels, p = 1 / (1 + e−delta/100), so the same +10 points is worth +0.73 pp against the shipped lawn baseline and +2.50 pp at neutral — a 3.4× spread. Printing one of those numbers asserts an opponent the player has not met. So the points are authoritative, the estimate is secondary, and the reference is named in the line or the estimate does not ship.

The one class that renders no estimate at all. StatusPotencyPoints feeds two different things from one number: a sigmoid decides whether a status lands, while netFactor = clamp(delta, 0, 10000) multiplies both its magnitude and its duration. An ungeared actor sits at delta = 1.0, so +1 status power doubles every status the wearer applies and the smallest authorable roll is a 2× multiplier. That is either an extraordinary affix class or a normalisation nobody wrote. Until it is answered, the raw magnitude renders and the estimate is suppressed — this kit does not render a number it cannot explain. spec-magnitude-and-units.md §3–§4 · OverlayCombatCalculator.cs:84–99 · ResistanceEvaluator.cs:155–217 · StatComposer.cs:24–31 · ShieldRuntime.cs:121, 403

Two matrices, and the difference is the contract, not the content. The combat table returns a relation where SAME is distinct from NEUTRAL and bakes K into RelationShare (±0.25); the shield table returns a bare unit −1 / 0 / +1, folds SAME into 0, and K is applied once downstream in ShieldMath from its own decoupled constant. One component cannot silently serve both — and it must be able to render the diff, because divergence is an Ask-first balance decision that has simply not happened yet.

Dual typing multiplies. combinedMult = m_primary × m_secondary, then bonus = (combinedMult − 1) × base. Fire into ice + earth is 1.25 × 1.0 − 1 = +0.25×; into air + earth it is 0.75 × 1.0 − 1 = −0.25×. A two-type defender is not “twice as resistant” — it lands anywhere in 0.5625× to 1.5625×.

Rows and columns are ordered by Ordinal, never alphabetically. The ordinal drives the generated channel set — combat.power.fire exists because fire is in the roster — so a re-sorted matrix would stop matching the stat sheet it sits beside. spec-shield-and-elements.md §0, §3.3–§3.5 · ElementTable.cs · ElementRingMatrix.cs · ShieldElementMatrix.cs · ElementHub.cs:16–24 · ElementPayload.cs:24–38

Three things this ladder settles that nothing in the shipped kit could.
1 — The value line is generated, not authored. Kind + channel + unit family + sign convention produce the sentence; content supplies numbers. Sign is per kind, not global: a negative resource.delta is damage, and a negative stat.modify on a lower-is-better channel is an improvement.
2 — Only a rolled line gets a bar. Five segments, and the three-way split comes straight from RollPolicy: Fixed gets no bar (a full bar would be a lie about the item's luck — nothing could have rolled otherwise), OnInstantiate gets one, and OnApply shows the band, because the item did not roll it, the hit does.

Six states, because a zero is four different things

150 active · default — real and gearable 0.95CAP capped 1.0 stub — no producer turn.haste unregistered — dev only
The state model is the Pending contract, applied to a stat. “My fire resist is 0” and “fire resist does not do anything yet” are different sentences, and a sheet rendering both as 0 has lied to the player about what to go and buy. Four of these states exist in shipped code right now: progression.power and progression.realm are hardcoded 1.0 stubs, so TierPower is 1.0 for every actor alive; progression.bonus.arm1/.arm2 and status.expose.* are registered and readable with no producer; and turn.speed, turn.haste and turn.moveSpeed are declared in DerivedTurnChannels.cs but not registered — ValidateChannel throws on all three.

Capped is a correctness case, not a nicety. The category resists cap at 0.95 and the flag families at 1, while status.resist.omni is uncapped — two cells in the same row obeying different rules. A player at the cap who stacks more resist gets literally nothing, and a bare 0.95 tells them to keep going.

The unit label lives on the group row, never in the cell. That is the magnitude document’s rule expressed as a layout constraint — it is what stops +150 crit rate and +12 fire power being read as comparable. spec-derived-stat-sheet.md §2–§4 · DerivedStatChannels.cs:110–146 · DerivedStatRegistry.cs:30–110 · DerivedComposer.cs:38–70 · DerivedTurnChannels.cs

A hit always spends at least 10% of its damage on the shield Penetration at best triples shield burn
100 damage reached 0 HP and cost 108 shield HP. That is not a rounding artefact. Fire is strong into the ice layer, so elemMod amplifies what the shield pays — and the same hit against a defender carrying +30 toughness per layer costs only 68 and never touches the innate shield at all. A single bar cannot say any of that, which is why the stack gets a per-layer readout.

The UI must never recompute remainder. It is proportional — (input × (toShield − spent) + toShield/2) / toShield — not input − spent. Re-deriving it as a subtraction gives a different number from the engine on almost every partial break. The server sends the cascade; the renderer renders it.

Four of the five apply outcomes are not “it worked”. Applied · Merged · DroppedWeaker (at the cap of three, and not stronger than the weakest) · Rejected (maxHp ≤ 0 after capacity) · MergedRemoved. A UI that only renders success cannot explain why a granted shield never appeared — GG-55 arriving from the runtime instead of from a button. spec-shield-and-elements.md §1–§3 · ShieldMath.cs:22–46 · ShieldPolicy.cs · ShieldRuntime.cs:288–345 · ShieldInstance.cs:36–48

F.4 The action bar — costs, targeting, and honest refusal

The shipped .actionslot (plate 04) only ever shows two states — affordable, or a bare-number is-unaffordable — with no resource identity and no way to say why an action is refused. Five typed refusals exist in the spec; the slot below shows four of them, additive to the existing component.

Five gates, cheapest first — every refusal named, none of them a bare disabled look

StrikeOnCooldown — 1 turn remaining
PyreCannotAfford(qi) — needs 50, has 12

Cost cluster — a list, not one pool; perTick drains, onCommit pays once

Stamina−12
Qi−4/tick

Stamina pays once at commit. Qi drains per resolve offset — if it projects to run dry before the last offset, the action ends early through the interrupt path. Both have already paid; nothing here refunds a missed hit.

Targeting — Chebyshev, never a circle; two range bands, never one colour

caster attack range — MaxRange 2 move range only — cannot attack from here without moving first
With no board, every one of these range checks passes. The grid above is what the range parameters become once the battle grid (A10) lands — today, with no board, targeting behaves exactly as it does now and excludes nobody. That is not a fallback drawn apologetically; it is the specific rule that keeps the basic attack byte-identical while the grid does not exist yet. The one loud exception: an Area-mode action is rejected at bind time while no board exists — shown as a real disabled state, never a silently empty target list.

Attack range and move range answer different questions — can I reach this target versus can I stand here — and rendering both as one colour would conflate them. The diamond shape is not a style choice: the shipped Square area of size n literally is a Chebyshev ball of radius (n−1)/2, so a circular range ring would promise cells the resolver does not grant. spec-action-layer.md §0, §3–§5 · action/spec-targeting.md §2, §4 · action/spec-usability-conditions.md §2 · action/spec-action-costs.md §3

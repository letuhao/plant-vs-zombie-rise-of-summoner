## 2. The structural insight — the combat block is a matrix, not a list

Eighty-four channels is unreadable as a list and trivially readable as a grid, because they are not
eighty-four things. They are **twelve families × seven element slots**, generated as exactly that:

```csharp
foreach (var family in CombatChannelFamilies) {          // 12
    ids.Add($"{family}.{ElementRoster.OmniId}");         // + omni
    foreach (var element in ElementRoster.Concrete)      // + 6
        ids.Add($"{family}.{element.ToElementId()}");
}
```

The UI must have the same shape as the generator, for the same reason the generator has it: **adding an
element or a family changes the grid by construction.** A hand-authored layout would need editing on
every roster change, and the roster has already changed once (light/dark, 2026-08-21) and the family
list once (the four `combat.shield.*` families).

| | omni | fire | ice | air | earth | light | dark |
|---|---|---|---|---|---|---|---|
| power · defense · crit rate · crit resist · crit damage · crit resist damage · accuracy · dodge · shield capacity · shield toughness · shield pen · shield regen | | | | | | | |

**Row order is the generator's order, not alphabetical** — offense families, then defense, then shield.
Sorting the rows by name would separate `crit.rate` from `crit.resist`, which are read as a pair.

### The omni column is not a seventh element

`omni` is an **additive baseline**, not a type — it adds into every element's effective total, and it is
never an actor type slot ([element-hub-ssot.md §4, §7](../architecture/element-hub-ssot.md)). The grid
renders it **first and visually separated** by a rule, so it never reads as "the seventh element". A
picker choosing an actor's element type must not offer it at all.

## 3. Six states, because zero is four different things

This is the part a naive sheet gets wrong. A channel showing `0` today may mean any of these, and they
demand different player responses:

| State | Means | Renders |
|---|---|---|
| **`active`** | non-zero, with contributions | the value, in its unit class |
| **`default`** | registered, nothing writes it, sitting at its default | the default, dimmed. **Not blank** — the channel is real and gearable |
| **`capped`** | at its registry cap — **the next point does nothing** | value + a `CAP` marker and the cap. Never the bare number |
| **`stub`** | the value is a hardcoded placeholder, not a computed one | the value + *"placeholder — the real curve is not built"* |
| **`no-producer`** | registered and readable, but nothing in the game can currently write it | *"nothing grants this yet"* |
| **`unregistered`** | the id exists in code but the registry **rejects** it | developer surfaces only, flagged red |

**`capped` is the one that is a correctness issue, not a nicety.** `status.resist.dot`, `.cc` and
`.contagion` cap at **0.95** ([DerivedStatRegistry.cs:46-48](../../src/FusionRpg.Core/Stats/Derived/DerivedStatRegistry.cs),
`Cap()` at `:135`), and `status.immune.*` / `status.immuneReduction.*` cap at **1**. A player at the cap
who stacks more resist gets **literally nothing**, and a sheet printing `0.95` with no marker has told
them to keep buying. Note the asymmetry, which is deliberate and must survive into the UI:
**`status.resist.omni` has no cap at all** ([actor-hub-ssot.md §3.D](../architecture/actor-hub-ssot.md)
— *"omni uncapped"*), so the omni cell and the category cells in the same row behave differently.

### The three states that exist right now, named

Verified in code this session, so the sheet ships with real examples rather than hypotheticals:

| Channel | State | Evidence |
|---|---|---|
| `progression.power`, `progression.realm` | **`stub`** | default `1.0` via `FlatReplace`, [DerivedStatRegistry.cs:35-36](../../src/FusionRpg.Core/Stats/Derived/DerivedStatRegistry.cs); `ActorDerivedSnapshot.StubNeutral()` hardcodes both to `1.0` ([:18-23](../../src/FusionRpg.Core/Stats/Derived/ActorDerivedSnapshot.cs)). `TierPower = power × realm` = 1.0 for every actor in the game |
| `progression.bonus.arm1`, `.arm2` | **`no-producer`** | registered and read, no writer |
| `status.expose.{category}` | **`no-producer`** | resolves at [:105-109](../../src/FusionRpg.Core/Stats/Derived/DerivedStatRegistry.cs), **zero readers** |
| `turn.speed`, `turn.haste`, `turn.moveSpeed` | **`unregistered`** | declared in [DerivedTurnChannels.cs](../../src/FusionRpg.Core/Battle/Timeline/DerivedTurnChannels.cs); `RegisterDefaults()` does not register them and `TryResolveChannel` has no `turn.` branch, so `ValidateChannel` throws `UnknownDerivedChannelException` |

> **Correction to the SSOT.** [actor-hub-ssot.md §11.4](../architecture/actor-hub-ssot.md) names
> *"`turn.speed` / `turn.haste`"* as the unregistered pair. There are **three** — `turn.moveSpeed` is
> declared on the same class. Minor, but the count is the kind of thing this sheet would surface, so it
> is fixed at the source.

**These four states are the `Pending<T>` contract, applied to a stat.** `absent` and `pending` looking
identical is the exact bug the sealed contract exists to prevent
([game-gui-map.md §Contract](../architecture/game-gui-map.md)), and a stat sheet is where a player is
most likely to meet it: *"my fire resist is 0"* and *"fire resist does not do anything yet"* are
different sentences and must look different.

## 4. Compose kind is player-facing, in plain words

Four kinds fold contributions differently
([DerivedComposer.cs:38-70](../../src/FusionRpg.Core/Stats/Derived/DerivedComposer.cs)), and the
difference is visible to anyone who adds a second source. **The term of art never ships; the behaviour
sentence does.**

| Kind | What it does | The line the player reads |
|---|---|---|
| `FlatSum` | `default + Σ Flat` | *"Sources add together."* |
| `FlatReplace` | highest `Priority` **wins outright**; ties broken ordinal by `SourceId`; only if no `Replace` exists does it sum flats | *"The strongest source wins — these do not add."* |
| `SumIncreased` | `default + Σ Increased`, **then capped** | *"Sources add, up to the cap."* |
| `MaxPriorityFlag` | `max()` over flag-ish mods | *"On or off — the strongest source decides."* |

**`FlatReplace` is the one that must be labelled**, because it is the only kind where the contribution
list does *not* sum to the total. A detail view listing three sources under a total that equals just one
of them looks like a bug unless the sheet says why. This affects `progression.power` and
`progression.realm` — the two `TierPower` inputs — so it is on the path of every status apply.

## 5. The three levels

Same ladder discipline as everywhere else: each level is built from the one below.

### 5.1 Summary — on the actor card, not the sheet

Six to eight lines, chosen by **what is non-default on this actor**, never a fixed list. Ends with a
*"see all N"* affordance carrying the real count. A fixed summary would hide the one channel a player's
build actually moved.

### 5.2 The sheet — a band-2 panel

```text
┌ Derived stats · Emberling ─────────────────────────────── [ Show unchanged ⃞ ] ┐
│  Combat                                      omni  fire  ice  air earth light dark │
│    Power                          game units   12   150    ·    ·    ·     ·    ·  │
│    Defense                        game units    ·     ·   40    ·    ·     ·    ·  │
│    Crit rate                   sigmoid points  150    ·    ·    ·    ·     ·    ·  │
│    …                                                                               │
│  Status                                                                            │
│    Resist · damage over time                   ·    0.95 CAP  ← next point does nothing │
│  Progression                                                                       │
│    Power                          placeholder  1.0   the real curve is not built   │
└────────────────────────────────────────────────────────────────────────────────────┘
```

**Zero-suppressed by default, with `Show unchanged` as a real toggle — not a hidden default.** Eighty-four
mostly-empty cells is noise; a permanently hidden channel is a thing the player cannot learn exists.
The toggle is persisted per player (`localStorage`, decision T4). **The count of what is hidden is always
visible**, so suppression never reads as absence.

**The unit label is on the group row, never in the cell** — this is
[spec-magnitude-and-units.md §3](spec-magnitude-and-units.md)'s rule expressed as a layout constraint,
and it is what stops `+150 crit rate` and `+12 fire power` being read as comparable. Guard 3 of that
document tests exactly this.

### 5.3 Channel detail — the "why"

Opened from a cell. Shows: the value, its unit class, the compose sentence from §4, the cap and distance
to it, and **the contribution list — each source named in the fiction's words**, never `sourceId`.

This is where the player answers *"where did this come from"*, and it is the only place the sheet can
honestly claim to explain a number.

> **What it cannot show yet, and must say so.** Four producers write derived channels today with **no
> registered subsystem row** — patron, stars, injuries, and contracts
> ([actor-hub-ssot.md §6.1](../architecture/actor-hub-ssot.md)). Until `stat.derived` lands and they
> adopt it, their contributions arrive **unattributed**. The detail view renders those as
> *"from your pact"* / *"from an injury"* where the producer is knowable and **an explicit
> `unattributed` row where it is not** — never silently folded into the total, which would make the
> list not add up with no explanation.

## 6. Open-ended families

The sheet cannot enumerate `status.power.{id}` ahead of time, and must not try.

| Rule | |
|---|---|
| **Render what the snapshot holds** | `ActorDerivedSnapshot.Channels` is the truth ([:35](../../src/FusionRpg.Core/Stats/Derived/ActorDerivedSnapshot.cs)) |
| **Plus the known expansion** | the 21 locked statuses × 2 families = 42 rows, shown as `default` when absent, because those are gearable and a player should know they exist |
| **Group `{statusId}` rows under their status**, not their family | a player thinks *"my Wither"*, not *"my status.power"* |
| **An unknown `{id}` still renders** | a channel arriving from a future status shows with its raw id in a neutral row rather than being dropped. **Dropping is the one unacceptable behaviour** — it makes a real bonus invisible |
| **`{tag}` flag families render as tags, never numbers** | `Immune to Freeze`, per the `Flag` unit class |

The component therefore binds to **`(channelId, value, unitClass, composeKind, cap, state)`** and has no
knowledge of which channels exist — the same registry-shape discipline the resource meter uses.

## 7. Guards

| # | Guard | Fails when |
|---|---|---|
| 1 | **The grid is generated, not authored** — row × column count equals `CombatChannelFamilies.Count × (ElementRoster.Concrete.Count + 1)` | someone hand-lists channels; breaks the moment an element or family is added |
| 2 | **Every rendered channel carries a state from §3** | a `0` ships without saying which kind of zero it is |
| 3 | **A capped channel at its cap renders the cap marker** | a player is told to keep stacking a dead stat |
| 4 | **No numeric column mixes unit classes** | inherits [spec-magnitude-and-units.md §8](spec-magnitude-and-units.md) guard 3 |
| 5 | **An unknown channel id renders rather than throwing or dropping** | a future status's channel silently vanishes |
| 6 | **`FlatReplace` channels render the compose sentence** | a contribution list does not sum to its total, with no explanation |
| 7 | **Volume fixture at 141 and at 300 channels** | the panel is only ever tested against a near-empty actor. GG-50 |
